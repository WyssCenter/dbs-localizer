# Running the pipeline: flags, environment variables, viewers

> Moved out of `AGENTS.md` (the *Documentation and checklist hygiene* → *Visualization* bullet) on 2026-10-12. Normative behaviour stays in `specs/*.md`; this is the operational reference. `dbsloc run --help` lists the current CLI surface.

normative D2/D3: `specs/08_visualization.md`; **interactive NIfTI QC viewer:** `specs/08_addendum_interactive_volume_viewer.md`. The matplotlib QC montages (`dbsloc viz mni-montage`, `reco-electrode-qc`) were retired 2026-10-12: use the checkreg viewer and the 3D scene. **Coreg/norm checkreg (Rust):** `dbsloc viz checkreg gen|review` → `gen` draws the check images in-process (`dbsloc_checkreg::gencheckregpair_png`), `review` starts `dbs-localizer checkreg` (`crates/dbsloc-viz`, `crates/dbsloc-app`); normative `specs/03_coregistration.md` §12. **Viewer program (2026-10-23):** the release ships only `dbs-localizer` and `dbsloc`; the viewers are modes of `dbs-localizer` (`dbs-localizer scene <options>`, `dbs-localizer checkreg <options>`); `dbsloc` finds it as `DBSLOC_GUI_BIN` → beside the running executable → `PATH` → `target/{release,debug}` of the source tree (`paths::gui_binary`). **Interactive 3D scene (template slices + Reco + optional atlas meshes):** `dbsloc viz scene --manifest <json>` → `dbs-localizer scene` (`cargo build -p dbsloc-app --release`); `DBSLOC_GUI_BIN`; headless validate: `--headless-check`; mouse bindings `--navigation lead-dbs|classic` (`dbsloc viz scene` forwards it; default `lead-dbs`, `specs/08` §11.1.5; the GUI persists the same choice from the viewer's *Mouse & touchpad* section). Default slices (`specs/08` §11.1.7, 2026-10-22, the reference implementation's default): sagittal and coronal through the world point (−30, −30, −30) mm, axial hidden; the *Backdrop* combo at the top of the viewer's *Slices* section chooses the image the slices show (template T1w / T2w, the subject's normalized post-op and pre-op images, installed downloads from `dbsloc backdrop list`, and in the GUI not-installed downloads and *Choose file…*); the Visualize stage lists them in the manifest under `backdrops`, the atlas, camera and mesh cache stay on `template_nii`. `dbs-localizer scene --backdrop <id>` starts on one of the manifest's backdrops (exit 2 on an id not in the list); `DBSLOC_SCENE3D_AUTOSAVE_PNG` waits for that load. After **reconstruct**, when **`RunOptions.normalization_template`** exists as a file, **`…/viz/scene_manifest.json` is always written**; `dbs-localizer scene` **opens by default** when a display is available (mirror checkreg UX): `--no-scene3d` or **`DBSLOC_OPEN_SCENE3D=0`** disables **launch only**; **`--headless`** / **`DBSLOC_HEADLESS=1`** skips the GUI but still writes the manifest; default redistributable atlas = AHEAD masks under `resources/atlases/ahead/structures_mni09b/` (`docs/ATLAS_AHEAD.md`); `DBSLOC_SCENE_ATLAS_LEAD_DIR` / `DBSLOC_SCENE_ATLAS_OBJ_DIR` / `DBSLOC_SCENE_ATLAS_NII` override atlas paths; `DBSLOC_SCENE3D_SKIP_NO_DISPLAY=1` when no UI. Atlas meshes are cached per user (`%LOCALAPPDATA%\dbsloc\cache\atlas_meshes` on Windows, `~/Library/Caches/dbsloc/atlas_meshes` on macOS, `$XDG_CACHE_HOME/dbsloc/atlas_meshes` else `~/.cache/dbsloc/atlas_meshes`) as `<stem>-<keyhash>.obj` + `<stem>-<keyhash>.cache.json` (key = mask and template hashes + meshing parameters), each written to a temporary file and renamed into place; a shipped `<stem>.obj` + `<stem>.cache.json` pair beside the masks is used first. DISTAL redistribution policy: `docs/ATLAS_DISTAL.md` (DISTAL Minimal bundled with the Lead-DBS licence statement beside it; other Lead-DBS atlases come from a Lead-DBS directory, and downloading them is specified in `specs/11` §10). From a **source tree** build, these are also resolved from workspace `target/release` then `target/debug` (and `$CARGO_TARGET_DIR/{release,debug}` when set) after `cargo build -p dbsloc-app --release` (`dbs-localizer` carries both viewer modes; the `checkreg-viewer` / `scene-viewer` cargo features of `dbsloc-viz` are library features the app enables). **Import images (GUI wizard, `specs/01` §8.4):** loose NIfTI files or DICOM folders → `rawdata/sub-<id>/ses-{preop,postop}/anat/` + `rawimages.json`, shared logic in `dbsloc_pipeline::import`; DICOM needs `dcm2niix`, resolved as `DBSLOC_DCM2NIIX_BIN` → `resources/dcm2niix/<platform>/` (bundled v1.0.20260724) → `PATH`. **Build and run:** `cargo build -p dbsloc-cli --release` produces `target/release/dbsloc` (`dbsloc.exe` on Windows); `cargo run -p dbsloc-cli --release -- <args>` builds and runs in one step. The `dbsloc` binary needs no Python or extension. **Pipeline (`dbsloc run`):** default stage list is the full Rust stage list (`dbsloc_pipeline::stage_names()`, through `visualize`); `--stages` takes stage names or the alias `coregister`, reports each under its canonical name (`coreg`) in the progress lines and the JSON summary, and exits 2 on an unknown or repeated name; **default** command runs preprocess/coreg/normalize and other implemented stage bodies; with `--reg-backend auto` on a machine whose GPU adapter passes the start-up self-test these run in-process (no ANTs process), otherwise the preprocess/coreg/normalize bodies need the bundled ANTs binaries. **`--plan`:** plan / lock behavior only (no N4/ANTs). Multi-slide checkreg after successful **coreg** (each coregistered pre-op or post-op image vs the anchor, `specs/03` §12.4a), **normalize** (normalized anchor, optional T2w, every normalized post-op image vs template), and **brainshift** when `sub.brainshift` is set is **on by default**; `--headless` or `DBSLOC_HEADLESS=1` skips `dbs-localizer checkreg` but still writes PNG/manifest and gates on method JSON (use `DBSLOC_CHECKREG_SKIP_NO_DISPLAY=1` + pre-approved log when there is no display). `--no-checkreg` or `DBSLOC_OPEN_CHECKREG=0` skips checkreg QC entirely. **GUI (`dbs-localizer`):** never starts a separate viewer process; with *Review registrations during the run* (default on) the run pauses after coreg / normalize and the slides appear in the *Registration review* tab (in-process review hook and PNG writer, `specs/03` §12.4a step 3 and 5); off = no QC during the run, *Review registration* on a finished step card still works. Scene viewer after **reconstruct**: **`--no-scene3d`** or **`DBSLOC_OPEN_SCENE3D=0`** skips opening `dbs-localizer scene` only (manifest still written when template path is valid). Approve coreg dict `approval`, norm/brainshift scalars; brainshift log `…/brainshift/log/sub-*_desc-brainshiftmethod.json`. See also `DBSLOC_STOP_ON_ERROR`, `DBSLOC_NORM_ISOTROPIC_MM` (SyN registration grid in millimetres; `full` = the full template grid without resampling; `template` or unset = the default: the template's own voxel size, 1.0 for the shipped template and 0.5 for the 0.5 mm catalogue templates, and on the GPU a default grid that does not fit the device steps to the finest coarser grid that does — 0.1 mm steps up to 1.0, then 1.5, 2.0, 2.5, 3.0 — printing `dbsloc: warning: normalize: registration grid stepped from the template's … mm to … mm: …` in the plan and the method log; an explicit value is never changed and the approved normalize lock re-runs on a differing grid only for an explicit value; same values as `--norm-isotropic-mm`, `specs/04` §5.1 step 2; the value is absolute millimetres from 0.3 to 3.0 (the range of the GUI's *Custom…* grid; anything else exits 2), and one finer than the template's own voxels only interpolates the template, so planning prints `dbsloc: warning: normalize: registration grid … is finer than the template's … mm voxels …` and the plan JSON lists it under `warnings`; the plan JSON also carries the effective `norm_isotropic_mm` and `norm_grid_source`), `DBSLOC_ANTS_MAX_THREADS`, `DBSLOC_TEMPLATE_T2` (T2 template of the multispectral SyN, `specs/04` §5.2; `--no-norm-multispectral` for T1-only); **registration engine of `ants_syn`** (`specs/04` §5.4, roadmap 3.18): `--reg-backend auto|wgpu|ants` / `DBSLOC_REG_BACKEND` (default `auto` = the GPU when a hardware adapter passes the device self-test, ANTs otherwise; `wgpu` = the GPU or an error; `ants` = the bundled processes), per-step overrides `--preprocess-backend` (N4 and precoreg), `--coregister-backend`, `--normalize-backend` (normalize, template bridge, point warps) with `auto|wgpu|ants` and the variables `DBSLOC_PREPROCESS_BACKEND`, `DBSLOC_COREGISTER_BACKEND`, `DBSLOC_NORMALIZE_BACKEND` (the flag wins; `--reg-backend` stays the default of every step; `specs/04` §5.4), adapter selection `DBSLOC_GPU_BACKEND` (`auto|vulkan|dx12|metal`), `DBSLOC_GPU_ADAPTER` (name substring), `DBSLOC_GPU_ALLOW_SOFTWARE=1` (software adapters are never used otherwise); the registration engine (`fastwarp/`) reads `FASTWARP_GPU_BACKEND`, `FASTWARP_GPU_ADAPTER`, `FASTWARP_GPU_ALLOW_SOFTWARE`, `FASTWARP_GPU_MEMORY_BUDGET_MB`, `FASTWARP_GPU_WAIT_TIMEOUT_S`, `FASTWARP_GPU_REQUIRE_ADAPTER`, `FASTWARP_GPU_BENCH`, `FASTWARP_ANTS_DIR`, `FASTWARP_ATLAS_INDEX_MAT`, `FASTWARP_UIPREFS_DIR`, `FASTWARP_REG_AB_DIR`, `FASTWARP_REG_ANTS_COMPOSITE` and `FASTWARP_REG_PROTO_DIR`, and for each of them still accepts the `DBSLOC_` name of the same suffix when the `FASTWARP_` one is unset (`FASTWARP_X` takes precedence when set); this product's commands, scripts and documentation use the `DBSLOC_` names, and the server's job environment (`JOB_ENV_KEEP`) forwards only `DBSLOC_*`; `dbsloc gpu probe [--json]` prints the adapter, graphics API and self-test verdict. When normalize runs on ANTs, its prerequisite check needs `antsRegistration` and, for a subject with a post-op image (CT or MR), `antsApplyTransforms` (`normalize: antsApplyTransforms not found (bundled or PATH)`). With the GPU backend the `preprocess` N4 and `normalize` need no ANTs binary and reconstruction maps points through `InverseComposite.h5` in Rust (the same lattice route as the coordinate-image route).

**Stages added 2026-10-12.** `precoreg` now runs by default (rigid anchor → template, header-only; once its image exists it is the anchor for coreg, normalize, checkreg and everything after; needs the template like normalize; `--no-coreg` drops it with coreg; `specs/02` §6.1). `coreg` also coregisters every post-op MR (`ax_MRI`, `cor_MRI`, `sag_MRI`), `normalize` carries them into template space and `reconstruct` on post-op MRI uses the normalized `ax_MRI` > `cor_MRI` > `sag_MRI` (`specs/03` §4 step 3). `orientation` estimates the roll of Boston and Abbott directional leads from the raw CT (experimental, `specs/06` §10; Medtronic SenSight reports `unsupported_model`) and rewrites the Reco `x` / `y` markers. **Invalidation** (`specs/00` §6.1): a stage that completes sets the locks of every stage depending on it to `approval: false` (`invalidated_by`, `invalidated_at`) and clears their checkreg approvals, printing `dbsloc: <stage> re-ran; approvals invalidated: …` even with `--log quiet`. **Own lock (2026-11-12, `specs/00` §6.1):** a `preprocess`, `precoreg`, `coreg`, `normalize` or `brainshift` that runs although its lock was approved (`--overwrite-approved`, another template / grid / method / `--reg-backend`, a changed fingerprint) withdraws its own approval before it starts (`dbsloc: <stage> runs again; its approval is withdrawn until the new result is approved`, `invalidated_by` = its own name); a lock that cannot be withdrawn fails the step before it runs (`<stage>: cannot withdraw its approval before it runs again: …`). The approval stays withdrawn after a stop at the gate, and after an error, a cancel or a killed process once the step has replaced an output; it is written back (only while the lock still reads as withdrawn by that step) when a `coreg` / `normalize` / `brainshift` is approved in its review during the same run (`…; its approval is kept`, with `--fingerprint-locks` carrying this run's input fingerprints), when the step body skipped without replacing an output, and when the step stopped before it replaced any output (a missing tool or template, a failed or cancelled registration: `dbsloc: note: <stage>: the step stopped before it replaced any output; its approval is kept`). A failed, cancelled or late-skipped step that replaced outputs (also a commit that failed part-way) invalidates the dependents as a completed one does; only writes made by this process are tracked. After `dbsloc run --headless` stops at the gate, `dbsloc lock approve <root> <subject> <stage>` and a new run continue (the stage is then skipped); with `--fingerprint-locks` add every path listed under `lock_input_paths.<stage>` in the JSON of `dbsloc run <root> <subject> --plan --fingerprint-locks` as `--input <path>`, otherwise the approval never skips the stage. Approving in the viewer leaves the lock unapproved, so a later `dbsloc run` runs the stage again.

**Electrode model (reconstruct, `specs/05` §3):** `--el-model '<catalogue name>'` (or `RunOptions.el_model`, GUI picker) wins; otherwise the `elmodel` entry of the subject's `prefs/sub-<id>_desc-uiprefs.mat` is used by the pipeline itself (the run log shows `dbsloc: note: reconstruct: electrode model from <path>: <model>`); with neither the stage fails with `no electrode model set`. **Reconstruction method and the `pacer` build feature (2026-11-13):** `--recon-method pacer` (`RunOptions.recon_method = "pacer"`, GUI method *PaCER*, server `recon_method`, PyO3 `reconstruct_ct(method="pacer")`) runs the AGPL-3.0-only crate `dbsloc-pacer` and exists only in builds with the cargo feature `pacer`, which the default build and the release packages include. A build without it (`--no-default-features`, `docs/LICENSING.md` *PaCER and the AGPL*) refuses that method with `E_RECON_pacer_unavailable: the reconstruction method pacer (--recon-method pacer) needs the optional PaCER component (licensed AGPL-3.0-only), which this build does not include; use auto or trac_core`: `dbsloc run --recon-method pacer` exits 2 before planning; the pipeline driver shared by the GUI, `dbsloc_pipeline_runner` and the server fails a run whose stages include reconstruct before its first stage starts (reported as a reconstruct failure; the reconstruct stage keeps the same check as a backstop); the server answers a run request with `recon_method = "pacer"` with HTTP 400 `E_RECON_pacer_unavailable` and leaves `pacer` out of its method list; the GUI shows the choice disabled as *PaCER (not in this build)* with an explanation and turns a saved PaCER choice into *Automatic* at start, with a note in the log. `auto` never runs the in-tree PaCER, in any build: on a CT it honours a pre-exported PaCER Reco v2 JSON (`DBSLOC_PACER_RECO_JSON` or `sub-<id>_desc-pacer_import.json`; reading it needs no PaCER code, so it also works without the feature) and otherwise runs native-frame TRAC/CORE. `--recon-bright-metal` (`RunOptions.recon_bright_metal`, GUI metal contrast *Bright*) applies to the post-op MRI path only: a post-op CT is always traced with its metal bright as scanned, and the setting there only logs `dbsloc: note: reconstruct: the bright metal setting does not apply to a post-op CT in HU; …`. **Lead-Tutor upload:** `dbsloc tutor submit-recon (--recon-json <file> | <dataset_root> <subject>)`, `dbsloc tutor submit-all-recon <dataset_root> [--require-all]` and `dbsloc tutor submit-file <payload.json> [--print-example]` post the MNI markers (`pt_<id>` → `leftElectrode` / `rightElectrode`, `head` / `tail` / `x`) to `--post-url` (default `LEAD_TUTOR_POST_URL`, else `http://tutor.lead-dbs.org:8000/my-endpoint`) with the header `User-ID` (`--user-id`, else `LEAD_TUTOR_USER_ID`, else the fixed cohort dashboard id `482197`; letters, digits, `.`, `_` and `-` only, anything else exits 2); the body carries only `pt_<id>` → `leftElectrode` / `rightElectrode` → `head` / `tail` / `x` with three JSON numbers each, so `submit-file` refuses any other key and any non-number; `submit-all-recon` skips (with a warning) a `sub-*` folder whose id is not one of the ten Lead-Tutor subjects; `--validate-only` and `--dry-run` run the same validation as the upload and never touch the network, `--no-open-browser` (`submit-file`: `--open-browser` opts in) controls opening the feedback page (`LEAD_TUTOR_DASHBOARD_URL`, default `http://tutor.lead-dbs.org/?userid=`). Exit 1 on validation, HTTP or network errors, 2 on usage errors.

**Run-option environment variables and precedence (2026-10-16):** `dbsloc run` and `dbsloc_pipeline_runner` resolve the run options through one function, `RunOptions::apply_env` (`crates/dbsloc-pipeline/src/options.rs`, list `RUN_OPTION_ENV`), with the usual precedence **explicit option or flag > environment variable > default**. The variables and the fields they fill: `DBSLOC_HEADLESS` → `headless`, `DBSLOC_OPEN_CHECKREG` → `checkreg`, `DBSLOC_OPEN_SCENE3D` → `no_scene3d` (inverted; `always` counts as on), `DBSLOC_STOP_ON_ERROR` → `stop_on_error`, `DBSLOC_REG_BACKEND` → `reg_backend`, `DBSLOC_PREPROCESS_BACKEND` / `DBSLOC_COREGISTER_BACKEND` / `DBSLOC_NORMALIZE_BACKEND` → the per-step engines, `DBSLOC_NORM_ISOTROPIC_MM` → `norm_isotropic_mm`, `DBSLOC_NORM_METHOD` → `norm_method`, `DBSLOC_ANTS_MAX_THREADS` → `ants_max_threads`, `DBSLOC_OUTPUT_DIR` → `output_dir`, `DBSLOC_POSTOP_MODALITY` → `postop_modality`, `DBSLOC_LEADDBS_ATLASES_DIR` → `leaddbs_atlases_dir` (2026-10-22; paths are made absolute, a blank value is unset). On / off variables accept `1`/`true`/`yes`/`on` and `0`/`false`/`no`/`off` (other values are ignored); a blank value is unset; an invalid engine, grid, method or thread count exits 2 with a message naming the variable, but only when that variable is consulted (an explicit flag or option makes the variable irrelevant, even an invalid one). For `dbsloc run` a field is explicit when its flag is given (`--headless`, `--no-checkreg`, `--no-scene3d`, `--norm-isotropic-mm`, `--norm-method`, `--reg-backend`, the per-step `--…-backend` flags, `--ants-max-threads`); `--no-checkreg` therefore wins over `DBSLOC_OPEN_CHECKREG=1`. For the runner a field is explicit when its key is present in the input JSON object (an explicit `null` counts; a key the writer omitted, for example the `skip_serializing_if` fields `reg_backend_*` and `norm_isotropic_mm`, is filled from the environment). **`stop_on_error` default (one rule for both):** explicit value, else `DBSLOC_STOP_ON_ERROR`, else the value of `checkreg` — on while the checkreg gate is on, off with `--no-checkreg` / `checkreg: false`; the gate itself always stops the run when a registration is not approved. The **GUI** (`dbs-localizer`) runs the pipeline in process with its own settings and reads none of these variables. The **server** sets every run option itself and removes every `DBSLOC_*` variable from the runner's environment except the tool and data locations `DBSLOC_ANTS_DIR`, `DBSLOC_DCM2NIIX_BIN`, `DBSLOC_REPO_ROOT`, `DBSLOC_DATA_DIR` (template catalogue directory), the template choice `DBSLOC_TEMPLATE_T1` / `DBSLOC_TEMPLATE_T2` (server configuration: the in-process `/plan` reads them too, so plan and run agree; `templates_dir` still wins because the server sets the template explicitly when it has one), `DBSLOC_GUI_BIN`, `DBSLOC_SCENE_ATLAS_LEAD_DIR`, `DBSLOC_SCENE_ATLAS_OBJ_DIR`, `DBSLOC_SCENE_ATLAS_NII` and the GPU adapter / budget variables `DBSLOC_GPU_*` (`dbsloc_server::runs::JOB_ENV_KEEP`); so `DBSLOC_PACER_RECO_JSON`, `DBSLOC_SCRF_*`, `DBSLOC_NO_BRIDGE` and the test switches in the server's environment do not change jobs.

**`dbsloc run` / `dbsloc lock` details (2026-10-15):** `--ants-max-threads N` and `--ants-max-threads=N` both set only the thread cap (never forwarded to ANTs); any other `--ants-<flag>[=value]` is passed through to `antsRegistration`; `antsApplyTransforms` (normalize apply) receives only the options it accepts — `--float`, `--verbose`, `--default-value`, `--output-data-type`, `--input-image-type` with their values — and the PaCER brain-mask resampling (`specs/02` §7.1) receives none. The warning that `--ants-…` options have no effect names the stages they need: the thread cap applies to preprocess, precoreg, coreg, normalize, brainshift and reconstruct, the other options to coreg and normalize, and neither to `--plan`. Ctrl-C during planning exits 130 too. The progress footer says `Pipeline finished all N step(s)`, `Pipeline stopped after K of N step(s)` or `Pipeline interrupted after K of N step(s)`, followed by the number of failed steps; a crash of the pipeline thread still prints the JSON summary with an `error:` row and exits 1. The hidden Python-era `--cprofile` / `--cprofile-out` flags are removed (usage error); use `--profile`. `dbsloc lock approve|show <root> <subject> <stage>` accepts the stage names of `--stages` (incl. `coregister`), writes / reads `locks/<canonical name>.json` (`coreg.json` for coregistration) and exits 2 on an unknown stage. `dbsloc reco show` reads no run environment variables; `dbsloc reco correct --source` accepts `gui` or `cli`.

**Manual correction (`specs/05` §9a, 2026-10-14):** `dbsloc reco show <dataset_root> <subject>` prints the edit space (`native` for a CT reconstruction, `mni` for the post-op MRI path), the backdrop image and each side's markers, roll and `manually_corrected` flag as JSON; `dbsloc reco correct <dataset_root> <subject> [--side right|left --head X,Y,Z --tail X,Y,Z [--roll DEG]] [--accept right|left]… [--space native|mni] [--source gui|cli] [--el-model M] [--template P] [--reg-backend auto|wgpu|ants] [--normalize-backend auto|wgpu|ants] [--no-index]` rebuilds the edited side's contacts from the electrode model, warps it into template (and reference) space, sets `props[side].manually_corrected` and records the side's review (`meta.manual_correction[side]`: `review` corrected, `roll_review`, an inputs fingerprint); `--accept` (repeatable) marks a side reviewed without changing it; it is refused (`E_RECON_manual`) when the side's coordinates were made with other inputs than the current ones (`meta.reconstruct.inputs` or the side's correction record), so run reconstruct first. `--side`, `--head` and `--tail` go together; giving neither them nor `--accept` exits 2 (`nothing to do`). The `reconstruct` lock is approved only once every lead is corrected or accepted, `orientation` once every directed lead's roll is set or accepted; `vat` / `visualize` are invalidated; a `CorrectionReport` is printed; exit 1 on `E_RECON_manual`, 2 on BIDS errors. The GUI's *Refine localization* view (`specs/08` §11.1.6, Reconstruct card, `Ctrl+6`, *Accept side*) does the same interactively. A later `dbsloc run` keeps every reviewed side (reconstruct re-traces only the others, orientation estimates only the unreviewed rolls) while the side's inputs fingerprint matches; when an upstream stage changed the inputs the review is dropped with a warning, and `--overwrite-approved` re-traces every side.

**Template (normalize, `specs/04` §3.1):** `--template <path|id>` or `DBSLOC_TEMPLATE_T1`, else the shipped `MNI152NLin2009bAsym_res-1mm` (`resources/templates/space/MNI152NLin2009bAsym/res-1mm/t1.nii.gz`, with `t2.nii.gz` beside it; ICBM 2009b at 1.0 mm, licence in `NOTICE`). An id is a catalogue id such as `MNI152NLin2009bAsym_res-0.5mm`, or a space name that maps to one entry; a downloadable entry that is not installed fails the stage with `template <id> is not installed; run: dbsloc template fetch <id>`. `dbsloc template list [--json]` shows each catalogue entry (bundled / installed / available with size); `dbsloc template fetch <id|space>` downloads one into the per-user data folder (progress on stderr, installed T1w path on stdout; exit 1 on error, 2 on an unknown id, 130 on Ctrl-C; SHA-256 checked, `specs/04` §3.2). **Scene backdrops** (`specs/08` §11.1.7): `dbsloc backdrop list [--json]` shows the downloadable 3D viewer backdrops (7T ex vivo brain, Edlow 2019, CC0: whole brain 0.5 mm, deep brain region 0.2 mm; installed / available with size); `dbsloc backdrop fetch <id>` downloads one to `<data folder>/backdrops/space/<space>/<id>/backdrop.nii.gz` (free-space check first, progress on stderr, installed path on stdout; exit 1 on error, 2 on an unknown id, 130 on Ctrl-C; SHA-256 checked; the 0.2 mm entry is cropped to the deep brain region after the download). **Lead-DBS atlases** (`specs/11` §10): `dbsloc atlas list [--json]` shows the 73 atlases of the Lead-DBS data package (bundled / installed / available, uncompressed size); `dbsloc atlas fetch <name>...` downloads each named atlas from the Lead-DBS host into `<data folder>/atlases/leaddbs/<name>/` (only that atlas's bytes, by HTTP range requests; every file checked against the pinned SHA-256 of `resources/atlases/leaddbs_download.json`; notice on stderr first, progress on stderr, installed folder on stdout; exit 0 all installed, 1 any failure, 2 unknown or bundled name, 130 on Ctrl-C); `dbsloc atlas remove <name>` deletes a downloaded atlas (exit 1 for a bundled, copied or missing one). Downloaded atlases are listed in the 3D scene as `user:<name>` beside the bundled and external ones. `DBSLOC_ATLAS_DOWNLOAD_URL` replaces the package address (pins still apply). Maintainers refresh the pins with `uv run python -I scripts/pin_leaddbs_atlases.py resources/atlases/leaddbs_download.json` when Lead-DBS replaces the package. Downloaded templates live in `DBSLOC_DATA_DIR`, else the per-user data folder (`%APPDATA%\dbsloc` on Windows). The template's space id (catalogue entry, `template.json`, a `space/<id>/` path component, else `custom-<sha256 prefix>`) is recorded in the normalization method log `normalization/log/sub-<id>_desc-normmethod.json` (`template_space`), the scene manifest and Reco v2 `meta.template_space`; an approved normalize lock re-runs when the recorded space differs. **Template space bridge** (`specs/04` §5.4a): for a template whose space is not `MNI152NLin2009bAsym`, `normalize` ends by building (once, cached under `<data folder>/templates/bridges/`) a SyN registration from the shipped reference template to it, and `reconstruct` adds a `reference` block (the `mni` coordinates mapped into the reference space) to the Reco file; Lead-Tutor submissions use that block. `DBSLOC_NO_BRIDGE=1` disables the bridge. The bridge also maps the TRAC search windows into the template and resamples the AHEAD atlas for the 3D scene (`specs/05` §4.3, `specs/08` §5). Check a bridge by hand: `cargo run -p dbsloc-pipeline --release --example bridge_check -- <target_t1> [auto|wgpu|ants]` (prints the cache directory, backend, seconds, the fitted target -> reference affine with its RMS residual and a few mapped points).

**GUI session log (2026-10-15):** every `dbs-localizer` session writes `%APPDATA%\dbsloc\logs\dbs-localizer-YYYYMMDD-HHMMSS-<pid>.log` (`$XDG_CONFIG_HOME/dbsloc/logs` or `~/.config/dbsloc/logs` on Linux, `~/Library/Application Support/dbsloc/logs` on macOS; override with `DBSLOC_LOG_DIR`), flushed after every line: a header (version, system, executable, display adapter, registration engine), run start with subject, steps and per-step engines, every Output-panel line, every error, panics with a backtrace, and on Windows a `FATAL native crash` line with the exception code. **Output folder (2026-10-22):** every command that reads or writes derivatives (`dbsloc run`, `reco show|correct`, `lock approve|show`, `tutor submit-recon|submit-all-recon`, `subject show`, `import`) takes `--output-dir <dir>`; default `<dataset>/derivatives/leaddbs`. `DBSLOC_OUTPUT_DIR` sets it for all of them (`RunOptions.output_dir`, same precedence rule as the other run-option variables: flag > variable > default; a relative path resolves against the current directory). **Version (2026-10-22):** `dbsloc --version` / `dbsloc version` print `dbsloc <version>+<git hash>` (`-dirty` when built from a tree with uncommitted changes); one workspace version (`[workspace.package]` in `Cargo.toml`, `docs/RELEASING.md`). **Normalization linear transform (2026-10-22):** normalize also writes the rigid+affine part of the warp as ITK binary `.mat` files beside the composites, `normalization/transformations/sub-<id>_from-anchorNative_to-<Space>_desc-affine_mode-image_xfm.mat` (ITK convention: maps template points to native points, as used to resample a native image onto the template) and `…_from-<Space>_to-anchorNative_desc-affine_mode-image_xfm.mat` (its inverse); both engines. For a non-reference template space the `mni` block is the `reference` block. An export problem is logged as a warning and never fails the stage; the JSON stays the primary file.

**Atlases (2026-10-22, `specs/11`):** the scene manifest lists every atlas set the catalogue finds (`atlas_lead_sets`, `atlas_default_id`): the bundled Lead-DBS folders under `resources/atlases/leaddbs/*` (ids `leaddbs:<folder>`; DISTAL Minimal is the default and carries its colours, opacities, presets and citation from `atlas_index.mat`), every folder of the Lead-DBS atlases directory (`--leaddbs-atlases-dir DIR` on `dbsloc run`, `RunOptions.leaddbs_atlases_dir`, env `DBSLOC_LEADDBS_ATLASES_DIR` with the run-option precedence rule, or the GUI setting *Lead-DBS atlases directory* on the Visualize card; a Lead-DBS install root or its `atlases` directory; ids `external:<folder>`; never copied; a subject's list changes on its next Reconstruct or Visualize run) and the bundled AHEAD masks (`ahead`). **Batch runs (2026-10-22, `specs/13` Part 2, `specs/00` §5.2):** `dbsloc run <root> <id> [<id>…]` runs several subjects one after another with the same options; `--all-subjects` takes every `sub-*` the dataset lists, `--subjects-file <txt>` adds one id per line (`#` comments). Subjects run sequentially (one ANTs / GPU job at a time); a subject that fails is reported with `dbsloc: warning: sub-<id> failed: … Moving on to the next subject.` and the batch continues (`--continue-on-error`, the default; `--stop-on-first-failure` marks the rest *not run*). Registration review in a batch: `--no-checkreg` turns the gate off, `--headless` or `--defer-review` (implies `--headless`) lets each subject stop at its unapproved gate (`awaiting_qc`, reviewed later with `dbsloc lock approve` / the GUI), otherwise the viewer opens per subject as for a single run. Output: a `=== Subject i/N: sub-<id> ===` header per subject, the usual progress, then a `subject | phase | ok/failed/skipped | seconds` table on stderr; with `--json` a single subject prints the unchanged summary object, several print `{batch: true, subjects: [<summary> + phase, message?, awaiting_stage?, seconds], totals: {…}, awaiting_qc: [ids], interrupted?}`. Exit 0 when no subject failed (awaiting review counts as not failed), 1 when any subject failed or was not found, 2 when every subject is unknown or on a usage error, 130 on Ctrl-C (the running subject and the rest are *cancelled*). **GUI:** tick boxes in the Subjects panel (*Select all* / *Select none*, ticks saved per dataset) turn *Run* into *Run (N subjects)*; the electrode picker offers *From each subject's settings* (`uiprefs.mat`); log lines are prefixed `[sub-<id>]`, errors are titled per subject, a results table appears at the end; *Stop* with subjects queued asks *Stop after this subject* / *Stop now* / *Keep running*; the review setting is *During the run* / *After all subjects* / *Off* (`StageSettings.review_mode`; *After all subjects* lets every subject stop at its gate and then opens the reviews one by one, approve queues that subject's remaining steps, reject marks it *needs rework*).

**Import (2026-10-22, `specs/01` §8.4, `specs/13` Part 1):** `dbsloc import <root> [--subject ID] [--output-dir DIR] [--dicom FOLDER]… [--nifti FILE]… [--item SESSION:SUFFIX[:ACQ]=SOURCE]… [--auto] [--postop-latest-study] [--no-keep-sourcedata] [--replace-existing] [--dry-run] [--json]` converts DICOM folders with the bundled dcm2niix (`-z y -b y -i y -f %f_%p_%z_%t_%s_%d`), suggests session / suffix / acq per series from the lookup table (last matching rule wins; keywords searched in SeriesDescription, ProtocolName and the file stem; sidecar `Modality: CT` = post-op CT; `DBSLOC_IMPORT_LOOKUP_JSON=<file>` replaces the table, shape `[{"session":"preop","suffix":"T1w","keywords":["t1","mprage"]}, …]`), `--item` overrides a suggestion (`SOURCE` = a file or `series:<N>`), unassigned images stop the run with exit 2 unless `--auto` leaves them out, `--postop-latest-study` turns the assigned pre-op MR series of the latest study into post-op MR when two or more dated studies exist, the source DICOM folders are archived under `sourcedata/sub-<id>/DICOM/` unless `--no-keep-sourcedata`, and `dataset_description.json` gains `GeneratedBy`. The default subject id is the first input folder's name (a folder named `DICOM` uses its parent), cleaned to letters and digits. The GUI wizard (*Import…*, `Ctrl+I`) does the same in the order Images → Subject and destination → Review, with several folders and several subjects at once (`specs/01` §8.4); screenshot mode `DBSLOC_APP_SCREENSHOT_ACTION=import` takes `DBSLOC_APP_IMPORT_INPUTS`, `DBSLOC_APP_IMPORT_ROOT`, `DBSLOC_APP_IMPORT_LATEST_STUDY` and `DBSLOC_APP_IMPORT_STEP=subject|review`. The GUI keeps the choice as a preference (`StageSettings.postop_modality`, set by the import wizard or the Coregister card) that it applies only to subjects having both post-op modalities, so a single-modality subject always runs as `auto`.
