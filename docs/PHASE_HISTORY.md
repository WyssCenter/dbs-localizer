> Moved out of `AGENTS.md` (former §5 Phase A/B/D task lists, §14 Progress Tracker and the §12 dated change log) on 2026-10-12. Current status lives in `AGENTS.md` §12; this file is the record.

## Phase task lists (former §5)

### Phase A — Analysis & Specification Planning — **✅ complete**

**Objective:** Fully understand the Lead-DBS MATLAB codebase; produce accurate, implementation-agnostic specifications for every module.

Tasks:

- Explore top-level codebase structure
- Map pipeline stages and key functions
- Read official documentation ([https://netstim.gitbook.io/leaddbs](https://netstim.gitbook.io/leaddbs))
- Deep-dive each pipeline module (one sub-agent per module)
- Identify all data structures (`Options` / `Subject` / `reco` MAT) — partial; `00_overview` + `01_bids` + recon `05` + Phase A archive overview section
- Catalogue all electrode models and their geometric parameters
- Catalogue all coordinate spaces and transform conventions
- Catalogue all normalization/coregistration method interfaces — see `02`–`04` specs
- Document external tool call signatures — per-module in `02`–`04` + `00`

### Phase B — Write Specifications — **✅ complete**

**Objective:** For each module identified in Phase A, write a precise, language-agnostic specification in `specs/`. Specs must be complete enough that a developer with no access to the MATLAB source can implement the module correctly.

Each spec document must contain:

- Purpose and scope
- Inputs (types, units, coordinate conventions)
- Outputs (types, units, coordinate conventions)
- Algorithm description (pseudocode or mathematical formulation)
- Edge cases and error conditions
- References (papers, not MATLAB code)
- Acceptance criteria / test cases

Tasks:

- `specs/00_overview.md` — pipeline orchestration & options struct
- `specs/01_bids.md` — BIDS layout, BIDSFetcher, subj struct
- `specs/02_preprocessing.md` — reorient, crop, bias correction, reslice
- `specs/03_coregistration.md` — method dispatch, QC, transform I/O
- `specs/04_normalization.md` — method dispatch, warp field format, SCRF
- `specs/05_reconstruction.md` — TRAC/CORE algorithm, PaCER interface, manual
- `specs/10_pacer.md` — PaCER full algorithm (clean-room target for `hpdbs-reconstruct::pacer`)
- `specs/06_orientation.md` — DiODe, FFT peak detection, rotation matrix
- `specs/07_vat.md` — analytical models (Kuncel, Dembek, Maedler), FEM interface
- `specs/08_visualization.md` — 2D slice output, 3D scene, atlas overlay
- `specs/09_electrode_models.md` — geometric params (73 models)

### Phase D — Validation & Testing

**Objective:** Validate output equivalence against Lead-DBS on the demo dataset.

Tasks:

- Run Lead-DBS on demo patient; save all intermediate outputs
- Run hp-dbs on same patient; compare outputs numerically
- Define tolerance thresholds per module (e.g., contact localization within 0.5 mm)
- Build CI pipeline (GitHub Actions)
- Performance benchmarks vs. MATLAB baseline

### Reconstruction status narrative (former §12 paragraph, 2026-09-11 → 2026-10-05)

**Both reconstruction methods work on real data as of 2026-09-11.** **PaCER** (`specs/10`, CT-only, the Lead-DBS default for CT) runs in the CT's native space and is now reachable: on `sub-76325` it finds both leads in 10 s with every level at 1496–2518 HU, the top 0.7% of the volume; phantom ground truth puts its worst level error at 0.437 mm. **TRAC/CORE** (`specs/05` §4.2, template space, the only option for post-op MRI) has along-shaft error ≤ 0.20 mm on a phantom across 6 leads and both metal polarities, and puts all 8 contacts of `sub-76325` in dense metal where the previous tracer had them in soft tissue. On CT, `auto` runs TRAC/CORE on the native coregistered CT and warps the points (roadmap 4.6, in Rust since 4.8); the Rust PaCER port is now calibrated on the distal metal edge and matches TRAC/CORE's accuracy on the Lead-Tutor sides it reconstructs (mean 1.37 vs 1.38 mm), but still refuses or misses leads on 3 of 10 subjects, so it is a cross-check, not the default (roadmap 2.22). `meta.tracer` and `meta.side_source` record what ran. **Still unverified: absolute accuracy on real data** — there is no expert reconstruction on disk (deferred OSF Tutor pull), so what is established is that the contacts are on the lead, not that they are on the right millimetre. The plausibility gate (1.8) proves internal consistency only; it passed a transposed volume that placed a lead outside the head (item 2.15), which sampling the CT at the reported coordinates caught. Since roadmap 4.8 / 4.9 every stage, including the post-op MRI template path, is a single Rust implementation behind the CLI, the runner and the GUI; the pure-Python centre-of-mass fallback (item 2.13) is deleted.
